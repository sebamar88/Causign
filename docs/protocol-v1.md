# Causign protocol v1

The normative structural contracts are the six JSON schemas shipped by `@causign/protocol`; the [approved design](superpowers/specs/2026-09-30-agentest-mvp-design.md) defines their lifecycle semantics. Generated TypeScript types represent these contracts. Scenario/result schema version `1` is separate from wire protocol `causign/1`.

Every frame contains protocol, unique message ID, type, timestamp and JSON payload. Execution frames include runId. An operationId is unique within its run; the pair identifies tool, approval or model activity. correlationId identifies a triggering message, rather than an operation. Timestamps are informational; receiveSequence records local arrival order, and correlations/lifecycle establish causality.

The runner sends hello; adapter.ready replies with supported versions, adapter identity/version and capabilities. Configure and adapter.configured finish negotiation before run.start/run.started. No common version or missing required capabilities is INCOMPATIBLE, with no run.start. Malformed or inconsistent advertisements are ERROR. Unknown capabilities are unsupported. `intercept.tools` requires tool request/result observation; `control.approvals` requires approval observation. Explicit requirements and requirements inferred from assertions/mocks are combined.

Valid reply correlations are hello → adapter.ready, configure → adapter.configured, run.start → run.started, run.cancel → acknowledged run.cancelled, intercepted tool.requested → tool.proceed/tool.mock/tool.reject, and approval.requested → approval.resolve. Replies preserve runId and operationId where applicable. Other lifecycle events omit correlationId. Spontaneous cancellation has no cancellation correlation. Duplicate IDs, wrong directions, unrelated existing trigger IDs, unknown operations, repeated decisions and terminal reactivation are violations.

tool.requested records intent before effects. An intercepted request waits for exactly one valid explicit decision. Proceed authorizes real execution and a tool.started fact; mock supplies a static result/error and bypasses real execution; reject blocks before execution. Timeout, disconnect, invalid commands and cancellation never authorize execution. Late decisions cannot reopen operations. tool.completed/tool.failed carries real/mock provenance. A started implementation that fails emits tool.failed; tool.rejected describes rejection before execution, with source and reason. Mocking is not a business approval. Unresolved approvals without configured decisions cause actionable ERROR and never grant by default.

Each started run has one terminal: completed, failed, cancelled or errored. Runner-generated errored terminals are explicitly marked source=runner and leave traces incomplete. Detected violations after a terminal make the scenario ERROR without replacing the terminal. A complete trace needs a valid adapter terminal, no detected loss, and promised evidence. The runner cannot prove concealed activity in an untrusted adapter.

Positive existential assertions pass with supporting facts; absent facts fail on complete traces and remain NOT_EVALUATED on incomplete traces. Negative assertions fail when the contrary fact exists, pass when absent with complete required observation, and remain NOT_EVALUATED when observation is incomplete. Real failure proves execution started but not successful completion. Mock errors do not satisfy successful-mock assertions. Results retain message/operation references and metric evidence; traces store facts rather than business-policy claims.

Latency uses the runner's monotonic clock from sending run.start to receiving its terminal. It includes transport/interception waiting and excludes negotiation, compilation, evaluation and reporting. Interrupted measurements are diagnostic. Costs require an explicit complete final amount with currency USD; tokens alone imply no price and core has no pricing table. Semantic evaluator verdicts include identity, explanation, configuration hash and provider/model when applicable; optional scores are not probabilities or statistical confidence.

Scenario PASS/FAIL differs from run terminals: completed can FAIL assertions, domain run.failed is FAIL, infrastructure/protocol/evaluator problems are ERROR, and insufficient unexplained evidence prevents PASS. Explicit scenario SKIP starts no adapter. Missing capabilities are INCOMPATIBLE. User interruption exits 130; timeout cancellation is ERROR/2 and spontaneous cancellation is ERROR. Suite precedence is ERROR/2 > INCOMPATIBLE/3 > FAIL/1 > PASS or SKIP/0. Empty suites are ERROR.

Managed stdin carries commands and stdout exclusively UTF-8 JSONL; stderr carries diagnostics. Executables and arguments are passed directly without a shell. Capture limits mark truncation and preserve partial invalid frames. One process per scenario provides state isolation, not a security sandbox. Unintercepted tools may have external effects, and model outputs remain nondeterministic.
